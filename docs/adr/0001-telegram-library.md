# ADR 0001: библиотека для Telegram Bot API

- Статус: принято к реализации; зафиксирована версия `v1.23.0`
- Дата: 23 августа 2026

## Контекст

`internal/tg` — небольшой собственный клиент для текстового моста. Он дал
точный контроль над offset, ретраями, ограничителем и тестовым Bot API. Для
четырёх методов это было оправдано.

Следующий этап требует двусторонних файлов, фото, callback queries, polls и
inline keyboards. Продолжать вручную описывать multipart, все варианты
`Message`, ошибки и новые версии Bot API — уже отдельный продукт внутри
проекта. При этом нельзя потерять наши гарантии: позиция `getUpdates` живёт в
JetStream и сдвигается после обработки, письмо дедуплицируется, адресация и
allowlist остаются доменной логикой моста.

## Решение

Использовать `github.com/go-telegram/bot` как набор моделей Bot API,
типизированный transport исходящих вызовов и реализацию multipart. Версия
зафиксирована: **`v1.23.0`** — последняя опубликованная на момент решения,
Bot API 10.2. «Последняя стабильная» как формулировка убрана намеренно: она
означала бы разные вещи в разное время, а весь аудит ниже относится к
конкретному коду.

Входящий long polling библиотеке **не** отдавать. В v1.23.0 `GetUpdates` и raw
request не экспортированы, а `Bot.Start` сдвигает приватный offset до передачи
обновления обработчику и сам задаёт retry polling. Это несовместимо с нашей
гарантией «offset после обработки». Наш код продолжает:

- сам вызывать `getUpdates` тонким HTTP-клиентом с offset из `bridge_state`;
- записывать новый offset только после обработки обновления;
- последовательно применять allowlist, маршрутизацию и дедупликацию;
- владеть ограничителем отправки и классификацией ошибок по области поражения;
- зависеть в `bridge` от узких интерфейсов, а не от объекта библиотеки.

Адаптер библиотеки заменяет исходящие HTTP/JSON/multipart и предоставляет
нужные операции: `GetMe`, `SendMessage`, topics, `GetFile`/download,
`SendDocument`/`SendPhoto`, inline keyboard, callback answer и polls. Для
`getUpdates` остаётся минимальная входящая HTTP-часть `internal/tg`; модели
обновлений берутся из библиотеки. Подмена server URL и HTTP client сохраняется,
чтобы `bridge.Run` целиком работал против двойника Bot API.

## Почему этот кандидат

На момент решения проект:

- следует актуальной ветке Bot API 10.x и регулярно выпускается;
- предоставляет типизированные методы с `context.Context`;
- поддерживает multipart `InputFile`, скачивание, callbacks, polls и webhooks;
- позволяет подменить server URL и HTTP client;
- не имеет транзитивных зависимостей.

Это покрывает расширение моста и сохраняет небольшую поверхность поставки.
Встроенный long polling намеренно не используется из-за порядка фиксации
offset, описанного выше.

## Что показал аудит v1.23.0

Проверено по исходникам зафиксированной версии. Два ограничения обязаны быть
в решении, а не только в переписке: они определяют, что миграция может
обещать, а чего нет.

**Числовой код ошибки из библиотеки не достаётся, и обходится это ниже её.**
Разбор ответа отображает `error_code` в собственные значения пакета, само
число не сохраняя: 403, 400, 401, 404 и 409 становятся sentinel-ошибками,
429 — типом с полем `RetryAfter`, всё прочее, включая 5xx, превращается в
текст. `Description` отдельным полем тоже нет.

У нас на числовом коде держится работающее поведение: `Permanent`,
распознавание недоступного канала и удалённой темы, классификация конфликта
в приёме. Терять его нельзя, а разбирать отформатированную строку ошибки —
нельзя тем более.

Поэтому код берётся **не из ошибки библиотеки, а из ответа**. Адаптер
оборачивает переданный `HttpClient`: на каждый вызов заводится capture,
привязанный к контексту этого вызова, обёртка в `Do` читает тело, возвращает
его библиотеке пригодным для чтения и — только при валидном конверте Telegram
с `ok=false` — запоминает HTTP-статус, описание и `retry_after`. После
возврата метода адаптер строит из capture точный `*tg.APIError` с теми же
полями, что и сегодня.

Это работает потому, что запрос создаётся с переданным контекстом
(`http.NewRequestWithContext`), а вызов `Do` ровно один: обёртка видит тот же
контекст и попадает в capture своего вызова, без общей изменяемой карты.

Sentinel-отображение остаётся только запасным путём для известных кодов, если
capture почему-то пуст. Неизвестный текст не разбирается.

`retry_after` из capture нужен единственной вещи — существующей паузе перед
повтором на 429. Публичный `tg.APIError` при этом не расширяется: сегодня в
нём три поля, и миграция сохраняет поведение, а не добавляет возможности.

Невалидное тело — не случай для capture. Прокси, ответивший на 5xx страницей
HTML, даст ошибку разбора, а не `APIError` с кодом; **так ведёт себя и
нынешний клиент**: он тоже сначала декодирует тело и лишь потом смотрит на
статус. Поведение сохраняется, новой границы здесь нет.

**Конструктор библиотеки возвращает ошибку, наш — нет.** `bot.New` отвергает
пустой токен сразу, а `tg.New` по сигнатуре ошибку вернуть не может.
Сигнатура `tg.New` сохраняется — за неё держится вызывающий код, и менять её
ради ошибки, которой в нашем пути не бывает (токен проверяется в конфигурации
раньше), не стоит. Ошибка создания запоминается и возвращается первым
исходящим вызовом; создаётся клиент без сети, с `WithSkipGetMe`. Ошибку
инициализации не выдавать за отказ Telegram: это разные вещи, и в журнале они
должны различаться.

**Подтверждено то, на чём стоит решение:** сеть в конструкторе отключается
опцией `WithSkipGetMe`; скрытых повторов запроса нет — ровно один вызов
`Do`, а тело собирается через `io.Pipe`, так что и стандартный клиент запрос
не переиграет; подмена адреса и HTTP-клиента доступна, причём клиент — узкий
интерфейс с одним методом; параметры отправки несут `MessageThreadID` и
`ParseMode`, то есть нашего поведения хватает без обходных путей.

## Рассмотренные альтернативы

### Оставить собственный клиент

Минимальная зависимость и полный контроль, но файлы и интерактивность резко
увеличивают объём протокольного кода. Мы начнём дублировать Bot API и постоянно
догонять его версии. Отклонено как основной путь.

Отклонено не целиком: входящий `getUpdates` остаётся собственным по причине из
раздела «Решение» — публичный API кандидата не позволяет сохранить порядок
«offset после обработки». То есть решение частично совпадает с этой
альтернативой, и это осознанно, а не по недосмотру.

### `gopkg.in/telebot.v4`

Высокоуровневый framework с удобными файлами, клавиатурами, callbacks,
middleware, публичным `Raw` и заменяемым `Poller`. Однако ветка v4 пока не имеет
стабильного релиза, а собственные Context и router сильнее вмешиваются в
архитектуру. Оставлен запасным вариантом: нужная точка расширения есть, но ради
неё сейчас не принимается риск beta-зависимости и более широкой интеграции.

### `go-telegram-bot-api/telegram-bot-api/v5`

Популярная низкоуровневая обёртка, но опубликованная стабильная ветка заметно
отстаёт от текущего Bot API: последний релиз v5.5 описывает Bot API 5.5.
Отклонено как основание для функций 2026 года.

## Порядок миграции

1. Добавить адаптер и parity-тесты трёх переносимых уже используемых методов
   (`GetMe`, `SendMessage`, `CreateForumTopic`), включая ошибки, split, rate
   limit, topics и тестовый server URL; отдельно сохранить тесты собственного
   `getUpdates` и порядка фиксации offset.
2. Перевести `bridge.Run` на адаптер без изменения пользовательского поведения;
   полный набор тестов и живая текстовая проверка обязаны остаться зелёными.
3. Удалить дублированный исходящий transport-код `internal/tg`, оставив
   минимальный входящий `getUpdates`, доменное форматирование и узкие интерфейсы.
4. Только затем реализовать объектную модель вложений.
5. После вложений добавить callback/poll модель вопросов.

Миграция делается отдельными обратимыми commit: смена transport не смешивается
с новой пользовательской функцией.

## Последствия и риски

- Появится новая прямая зависимость; обновления версии проходят через тесты и
  просмотр changelog.
- Политикой повторов владеет мост; автоматически повторять можно только
  операции с доказанной идемпотентностью. Для `v1.23.0` скрытых повторов нет —
  см. раздел про аудит выше, — но при каждом обновлении зависимости это
  проверяется заново. Если внутренние повторы неидемпотентных `send*`
  появятся, их отключают либо доказывают отсутствие тестом: повторный
  `sendMessage` создаёт второй пост, обходя нашу отметку показа.
- Типы Telegram не выходят в `mail.Message` и MCP API: иначе смена библиотеки
  станет изменением протокола всей сети.
- Автоматический worker pool библиотеки не включается: параллельная обработка
  может переставить offset раньше незавершённого обновления.
- Токен никогда не логируется. File download URL краткоживущая и содержит
  токен в пути, поэтому не сохраняется в письмах и логах.
- Все входящие файлы, captions и callback payload остаются недоверенными
  данными; allowlist пользователя применяется до побочных эффектов.
