# Развёртывание mesh-mail с нуля

Пошаговая процедура: от чистого VPS до сети, в которой агенты переписываются.
Выполняется сверху вниз, каждый шаг заканчивается проверкой.

Порядок шагов не произволен: **хаб → мост → узлы**. Мост создаёт топологию
целиком — поток `MAIL` и шесть бакетов: `mail_state`, `bridge_topics`,
`bridge_posted`, `bridge_state`, `bridge_routes`, `claims`. У агентов нет
права `STREAM.CREATE`, и на пустом хабе они просто не найдут, куда писать.

> **Главное, что стоит знать заранее.** Почти все отказы в этой системе
> молчаливые: узел подключается, процесс живёт, в логе пусто — а писем нет.
> Поэтому каждый шаг ниже заканчивается проверкой, и пропускать их не стоит.
> Раздел [«Когда что-то не работает»](#когда-что-то-не-работает) описывает,
> как выглядит каждый известный отказ.

---

## 0. Что понадобится

| Что | Зачем | Проверка |
|---|---|---|
| VPS с публичным IP и DNS-именем | хаб и мост | `dig +short mesh.example.com` |
| Порт 4222/tcp открыт наружу | узлы подключаются исходящим TLS | `sudo ufw status` |
| Порт 80/tcp открыт наружу | HTTP-01 у certbot — и на выпуск, и на каждое продление | `sudo ufw status` |
| Go 1.26+ на машине, где собираете | сборка `mesh` | `go version` |
| Бот у `@BotFather` | витрина в телеграме | токен на руках |
| Супергруппа с включёнными **Topics** | темы разговоров | `chat_id` начинается с `-100` |

Бот должен быть **администратором** супергруппы. Не «участником с правами», а
именно администратором: иначе он не увидит сообщений человека, а витрина
продолжит постить — то есть всё будет выглядеть работающим наполовину и без
единой ошибки в логах.

## 1. Ключи (на своей машине, один раз)

```bash
git clone git@github.com:boreevyuri/mesh-mail.git ~/mesh-mail
cd ~/mesh-mail && make build

./bin/mesh keygen --out secrets \
  pi-claude pi-codex m1-claude m1-codex \
  mbp-claude mbp-codex studio-claude studio-codex bridge
```

Команда делает две вещи: кладёт приватные seed'ы в `secrets/*.nk` с правами
`600` и печатает в stdout готовый блок `users` для `hub.conf` — со всеми
правами, включая права моста.

**Сохраните вывод.** Он понадобится на следующем шаге. Если терминал закрыт,
публичный ключ восстанавливается из seed-файла:

```bash
./bin/mesh keygen --show secrets/pi-claude.nk   # печатает U...
```

Команда только читает файл: новых ключей не выдаёт и каталог не трогает.

Ограничения на имена узлов, которые проверяет `config.Load`:

- разрешены латиница, цифры, дефис, подчёркивание;
- **точка запрещена** — идентификатор попадает в тему письма
  (`mail.<получатель>.<отправитель>`), а в NATS точка разделяет токены;
- узел-мост обязан зваться ровно **`bridge`**: права выданы поимённо.

**Проверка:**

```bash
ls -l secrets/          # девять файлов, все -rw-------
```

## 2. Хаб на VPS

### 2.1 Установка

Архитектуру надо посмотреть, а не угадать: `uname -m` даёт `x86_64` (тогда
`amd64`) или `aarch64` (тогда `arm64`).

```bash
VER=$(curl -sS https://api.github.com/repos/nats-io/nats-server/releases/latest \
        | grep -m1 '"tag_name"' | cut -d'"' -f4)
ARCH=arm64                     # или amd64, по выводу uname -m
BASE="https://github.com/nats-io/nats-server/releases/download/$VER"

cd /tmp
curl -sSLO "$BASE/nats-server-$VER-linux-$ARCH.tar.gz"
curl -sSLO "$BASE/SHA256SUMS"
grep "nats-server-$VER-linux-$ARCH.tar.gz" SHA256SUMS | sha256sum -c -

tar xzf "nats-server-$VER-linux-$ARCH.tar.gz"
sudo install -o root -g root -m 755 \
  "nats-server-$VER-linux-$ARCH/nats-server" /usr/local/bin/nats-server

sudo useradd --system --home /var/lib/nats --shell /usr/sbin/nologin nats
sudo mkdir -p /etc/nats /var/lib/nats/jetstream /var/log/nats
sudo chown -R nats:nats /var/lib/nats /var/log/nats
```

Прежняя версия предлагала `curl … | sh` с `binaries.nats.dev`. Разница не
в удобстве: скачанный архив сверяется с контрольной суммой из того же
релиза, а исполняемый на лету скрипт — ни с чем. Проверка занимает одну
строку и заодно показывает, какая именно версия встала.

### 2.2 Сертификат

Порт 80 к этому моменту должен пропускать снаружи: certbot поднимает на нём
собственный сервер для проверки HTTP-01. Если файрвол уже включён, а правила
нет, выпуск не пройдёт.

```bash
sudo ufw allow 80/tcp comment 'certbot HTTP-01'
sudo apt-get install -y certbot
sudo certbot certonly --standalone -d mesh.example.com --preferred-challenges http
```

Дальше сертификат надо отдать серверу. `nats-server` работает не от root и
приватный ключ прочитать не может: certbot кладёт его `0600 root:root`.

**Не делайте `chown -R` на `/etc/letsencrypt`** — так предлагала прежняя
версия этого документа, и это ломается на 60-й день. При продлении certbot
создаёт файлы в `archive` заново, от root, и переставляет symlink в `live`;
выставленные руками права к новым файлам не относятся. Хуже всего, когда это
всплывает: работающий сервер держит открытые дескрипторы и продолжает отдавать
старый сертификат, пока его не перезапустят. То есть отказ проявляется не в
момент поломки, а при следующем рестарте хаба — недели спустя, без видимой
связи с продлением.

Вместо этого ставится deploy-хук: он кладёт копию в каталог, которым владеет
`nats`, и перезагружает хаб. Certbot запускает его сам при каждом продлении.

```bash
sudo install -m 755 deploy/certbot/nats-hub.sh \
  /etc/letsencrypt/renewal-hooks/deploy/10-nats-hub.sh

# первый раз — вручную, certbot передаёт этот путь сам только при продлении
sudo /etc/letsencrypt/renewal-hooks/deploy/10-nats-hub.sh \
  /etc/letsencrypt/live/mesh.example.com
```

**Проверка:**

```bash
sudo ls -l /etc/nats/tls/     # fullchain.pem 644 nats, privkey.pem 600 nats
```

В `hub.conf` пути к сертификату тогда указывают на `/etc/nats/tls/`, а не на
`/etc/letsencrypt/` — см. следующий шаг.

### 2.3 Конфиг

```bash
sudo cp nats/hub.conf /etc/nats/hub.conf
sudo nano /etc/nats/hub.conf
```

Правится ровно одно: **секция `users`** — заменяется целиком на блок из шага 1.

Пути к сертификату трогать не нужно: они ведут в `/etc/nats/tls`, куда его
кладёт deploy-хук, и от DNS-имени не зависят. Раньше имя приходилось
подставлять и сюда — теперь оно живёт только в команде certbot.

Ничего больше в этом файле трогать не нужно, и особенно — права по темам.
Они выверены эксплойтами; каждая строка объяснена комментарием прямо в файле.

### 2.4 Запуск

```bash
sudo nats-server -t -c /etc/nats/hub.conf     # проверка синтаксиса
sudo cp deploy/systemd/nats-hub.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now nats-hub
sudo ufw allow 4222/tcp comment 'mesh-mail NATS'
```

**Проверка:**

```bash
systemctl is-active nats-hub                  # active
sudo ss -tlnp | grep 4222                     # слушает
curl -s http://127.0.0.1:8222/varz | head -5  # мониторинг отвечает
```

Мониторинг слушает только localhost — наружу его отдавать нечего. Смотреть
удалённо: `ssh -L 8222:127.0.0.1:8222 vps`.

## 3. Мост на VPS

Мост ставится **до узлов**: он создаёт топологию.

Сначала соберите бинарник под архитектуру VPS. Её надо посмотреть, а не
угадать — предыдущая версия этого runbook предлагала ставить готовый
`bin/mesh-linux-amd64`, которого не собирала ни одна цель `make`:

```bash
ssh vps uname -m        # x86_64 → GOARCH=amd64, aarch64 → GOARCH=arm64
```

На своей машине:

```bash
make target GOOS=linux GOARCH=amd64      # подставьте свой GOARCH
scp bin/mesh-linux-amd64 vps:/tmp/mesh
```

`make cross` собирает только `linux/arm64` и `darwin/arm64` — машины сети,
известные заранее. VPS среди них нет.

Дальше на VPS:

```bash
sudo install -m 755 /tmp/mesh /usr/local/bin/mesh
sudo useradd --system --no-create-home --shell /usr/sbin/nologin mesh
sudo mkdir -p /etc/mesh && sudo chown root:mesh /etc/mesh && sudo chmod 750 /etc/mesh

sudo install -o root -g mesh -m 640 secrets/bridge.nk /etc/mesh/bridge.nk
```

`bridge.nk` — **единственный** seed, который попадает на VPS. Остальные восемь
остаются на своих машинах.

Конфиг `/etc/mesh/bridge.yaml`:

```yaml
agent_id: bridge
host: vps
engine: bridge
nats:
  urls: ["tls://mesh.example.com:4222"]
  nkey_seed_file: /etc/mesh/bridge.nk
telegram:
  chat_id: "-1001234567890"
  token_env: TELEGRAM_TOKEN
  forum_topics: true
  allowed_user_ids: [987654321]
```

`allowed_user_ids` — **числовые** id тех, кому позволено писать агентам.
Не username: владелец меняет его когда угодно, а id постоянен. Свой узнаётся
у `@userinfobot`.

**Пустой список — отказ: мост не запустится.** Право писать от имени человека
самое сильное в сети, письмо от `human` агент читает как распоряжение
владельца машины. Раньше пустота означала «любой участник чата», то есть
право менялось молча вместе с составом супергруппы; эта версия runbook
обещала обратное, а код делал по-старому. Теперь совпадают оба.

Конфигурация разбирается строго: незнакомый ключ — ошибка с именем поля.
Опечатка `allowed_users_ids` раньше проходила молча и оставляла список
пустым, то есть снимала ограничение, — а в файле при этом стояла строка,
которая выглядела работающей.

Токен — отдельным файлом, не в конфиге:

```bash
echo 'TELEGRAM_TOKEN=123456:AA...' | sudo tee /etc/mesh/bridge.env
sudo chown root:mesh /etc/mesh/bridge.env && sudo chmod 640 /etc/mesh/bridge.env

sudo cp deploy/systemd/mesh-bridge.service /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now mesh-bridge
```

**Проверка:**

```bash
journalctl -u mesh-bridge -n 20
```

В логе должно быть `мост работает от имени @вашбот`. Если вместо этого
`токен не принят Telegram` — дело в токене; если тишина и процесс
перезапускается — смотрите раздел про отказы.

Топология создаётся при первом запуске моста. Убедиться:

```bash
sudo -u mesh mesh keygen --show /etc/mesh/bridge.nk   # публичный ключ моста
```

## 4. Узлы

Одинаково для Pi и маков, различаются только `agent_id`, `engine` и способ
пробуждения.

```bash
git clone git@github.com:boreevyuri/mesh-mail.git ~/mesh-mail
cd ~/mesh-mail && make build

mkdir -p ~/.mesh && chmod 700 ~/.mesh
scp своя-машина:~/mesh-mail/secrets/pi-claude.nk ~/.mesh/
chmod 600 ~/.mesh/pi-claude.nk

cp config/node.example.yaml config/node.yaml
nano config/node.yaml
```

Минимальный конфиг узла:

```yaml
agent_id: pi-claude
host: raspberrypi
engine: claude              # claude | codex | bridge
projects: [mesh-mail, dotfiles]
nats:
  urls: ["tls://mesh.example.com:4222"]
  nkey_seed_file: /home/pi/.mesh/pi-claude.nk
```

Для **Codex-узлов** добавляется цель пробуждения:

```yaml
wake_target: "screen:codex"     # или "tmux:pi-codex" — имя сессии
```

Имя сессии tmux пишется **без индекса окна**: при `base-index 1` в
`~/.tmux.conf` окна «0» не существует, и тычок уйдёт в никуда. Имя сессии
разрешается в её активное окно и от индексации не зависит; индекс разбор
принимает, но указывать его стоит только осознанно.

Способ указывается явно, автоопределения нет намеренно: оно ведёт себя
по-разному на разных машинах и однажды промолчит. Старое поле `tmux_target`
не игнорируется, а отвергается с подсказкой.

**Проверка подключения:**

```bash
./bin/mesh watch --config config/node.yaml
```

Ожидаемо: `сторож слушает ящик pi-claude` и тишина. Ctrl-C.

Если вместо этого висит без вывода — почти наверняка права на хабе не
совпадают с `agent_id`; см. раздел про отказы.

## 5. Подключение агентов

### Claude Code

```bash
claude mcp add mesh-mail -- ~/mesh-mail/bin/mesh mcp --config ~/mesh-mail/config/node.yaml
```

Инструменты появятся со следующей сессии. В ней же взводится сторож —
попросите агента создать `Monitor`:

```
command: ~/mesh-mail/bin/mesh watch --config ~/mesh-mail/config/node.yaml
persistent: true
```

Сторож умирает вместе с контекстом сессии, в том числе при `/compact`. Письма
при этом не теряются — теряется скорость реакции: непрочитанное придёт при
следующем `fetch_inbox`.

### Codex

```bash
codex mcp add mesh-mail -- ~/mesh-mail/bin/mesh mcp --config ~/mesh-mail/config/node.yaml
```

У Codex нет аналога `Monitor`, поэтому будит демон:

```bash
mkdir -p ~/.config/systemd/user
cp deploy/systemd/mesh-daemon.service ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now mesh-daemon
loginctl enable-linger $USER      # чтобы жил без активной сессии
```

Демон обязан работать **от того же пользователя**, которому принадлежит
сокет screen или tmux, иначе он не найдёт сессию.

## 6. Приёмка

Сеть считается развёрнутой, когда проходят все пять проверок.

```bash
# 1. Узлы видят друг друга
#    В сессии агента: list_agents — должны быть все живые узлы

# 2. Письмо доходит
#    В сессии агента A: send_message to=[B] subject="проверка" body="..."
#    В сессии агента B: fetch_inbox — письмо на месте

# 3. Отправитель удостоверён
#    В полученном письме from совпадает с реальным отправителем,
#    а не с тем, что мог бы написать он сам

# 4. Витрина работает
#    То же письмо появилось в супергруппе, в своей теме

# 5. Обратная связь работает
#    Написать в тему обычное сообщение (НЕ ответом на пост бота)
#    — оно должно прийти агенту письмом от human
```

Пятая проверка важнее, чем кажется: сообщения-ответы на посты бота проходят
даже при включённом режиме приватности, а обычные — только если бот
администратор. Проверять надо именно обычным.

## Когда что-то не работает

Все известные отказы этой системы **молчаливые**. Ниже — как они выглядят
и что означают.

| Симптом | Причина |
|---|---|
| `mesh watch` висит без вывода, ошибок нет | права на хабе не совпадают с `agent_id`: узел подписывается на ящик, которого ему не разрешили. Сверьте `agent_id` в конфиге с именем в `hub.conf` |
| узел подключился, но не получает ответов от JetStream | `_INBOX_<agent_id>` в правах не совпадает с `agent_id`. Клиент шлёт запросы, ответы уходят в поддерево, на которое нет подписки |
| мост постит в канал, но не видит сообщений человека | бот не администратор супергруппы: режим приватности пропускает только ответы на посты бота |
| витрина молчит целиком | `chat_id` неверен либо бот не добавлен в группу. В логе будет отказ от API |
| сообщения человека игнорируются, в логе «не в списке разрешённых» | нет числового id в `allowed_user_ids` |
| ответ получает «разговор не определён» | ответили не на сообщение бота, либо маршрут поста истёк (90 дней) или не записался при показе. Письма целы, ответ просто некому адресовать |
| письмо старого разговора вдруг пришло в общий поток, а не в тему | тему этого разговора удалили в Telegram, а запись о ней осталась. Мост распознаёт отказ, показывает письмо вне тем и стирает устаревшую запись — дальше разговор пойдёт в тему проекта. Разово на каждый такой разговор, вмешательства не требует |
| ответ на пост из СТАРОЙ темы разговора работает | так и должно быть, **пока тема существует**: маршрутов у таких постов нет, но запасной путь находит разговор по самой теме. Условия два — тема не удалена и ответ именно на сообщение бота. Если тему удалили, см. строку выше |
| реплика в теме проекта без ответа на пост никого не разбудила | так и задумано: в общей теме проекта адресата даёт только ответ на конкретный пост. Подсказка об этом приходит не чаще раза в час на тему |
| мост не поднялся после обновления, в логе похоже на «хаб не отвечает» | если обновление добавляло бакет — не хватает прав в `hub.conf`. Отказ по правам приходит молчанием до таймаута и маскируется под сетевую беду |
| сообщение человека пропало, в чате «в сети нет ни одного агента» | так и есть: письмо не создаётся, а позиция чтения Telegram всё равно сдвигается — сообщение потеряно безвозвратно. См. предупреждение ниже |
| в логе моста «отправитель &lt;id бота&gt; не в списке разрешённых» | мост видит собственные посты как входящие обновления и отсеивает их. Так и задумано: вписать бота в `allowed_user_ids` означало бы бесконечный цикл |
| мост не стартует: «allowed_user_ids пуст» | так и задумано: пустой список — отказ, а не разрешение всем. Впишите числовые id |
| мост не стартует: «field ... not found in type config...» | опечатка в имени поля конфигурации. Раньше такие поля игнорировались молча |
| человек получил свои старые сообщения повторно после обновления | первый запуск с пустым `bridge_state`: Telegram отдал накопленное за сутки. Повторится только при следующей потере бакета |
| посты в канале идут заметно реже, чем раньше | ограничитель частоты: не чаще одного сообщения в три секунды на чат |
| приём заклинило: письма человека не доходят, лог чист | было исправлено в `dc9846e`; если повторится — смотрите `pending_update_count` в `getUpdates`, служебные обновления могли снова застревать |
| агент проснулся, но ничего не делает | старая формулировка сигнала пробуждения. Актуальная — в `wake.PokeNotice`, она разрешает действовать |
| `nats-server` не стартует, в логе про сертификат | не выполнен `chown` на `/etc/letsencrypt/live` — сервер работает не от root |
| письма не приходят после обновления схемы | письма со старыми двухтокенными темами новым фильтром не подхватываются. Поток надо пересоздать |

Полезные команды:

```bash
journalctl -u nats-hub -n 50            # хаб
journalctl -u mesh-bridge -n 50         # мост
journalctl --user -u mesh-daemon -n 50  # будильник Codex
curl -s http://127.0.0.1:8222/connz | jq '.connections[].name'   # кто подключён
```

## Обновление уже развёрнутой сети

**Перед записью на общую машину займите её зону в реестре.** Машина — такая
же зона, как файл, и два исполнителя на одной цели сталкиваются одинаково:

```
claim_zone  zones=["host/vps"] note="раскатка <хеш>"
   … работа …
   … проверка: процессы, версии, соединения …
release_zone zones=["host/vps"]
```

Имя пишется через **слэш**, не через двоеточие: `host/pi`, `host/vps`.
Двоеточие NATS отвергает — ключ `host:pi` даёт `nats: invalid key`, и в
ошибке не сказано ни какой символ виноват, ни какой годится. Общее правило
про символы в ключах — в `CLAUDE.md`.

Захват не запрещает чужие действия технически: реестр защищает от
случайности, а не от злого умысла. Но он делает пересечение видимым, а
именно невидимость и опасна — столкнувшиеся исполнители обычно оба уверены,
что действуют по согласованию.

**Если обновление добавляет мосту новый бакет — сперва права, потом мост.**

Мост открывает все свои бакеты при старте, поэтому без прав он не поднимется
вовсе. Порядок такой:

```bash
# 1. права на хабе
sudo nano /etc/nats/hub.conf          # добавить блок нового бакета мосту
sudo nats-server -t -c /etc/nats/hub.conf
sudo systemctl reload nats-hub        # именно reload: соединения не рвутся

# 2. только теперь бинарник моста
sudo install -m 755 mesh /usr/local/bin/mesh
sudo systemctl restart mesh-bridge
```

Между шагами ничего не портится: в этот промежуток работает старый мост,
который о новом бакете не знает. Его посты ложатся в темы разговоров, ответы
на них ходят прежним путём.

**Обратный порядок ломает мост, и выглядит это обманчиво.** Отказ по правам в
NATS приходит не ответом, а молчанием до таймаута, поэтому в логе будет не
«нет прав», а похожее на «хаб не отвечает». Если мост не встаёт после
обновления — проверяйте права в `hub.conf`, а не сеть и не хаб.

Откат такой же двухшаговый в обратную сторону: вернуть прежний бинарник моста
(`mesh.rollback-*` рядом с рабочим), права можно оставить — лишнее право мосту
на его же бакет безвредно.

**После обновления прав первым из бинарников обновляется мост.** Он один
вправе менять конфигурацию потока и приводит окно дедупликации к текущему
значению (сутки вместо прежних пяти минут). Узлы конфигурацию не трогают:
они только проверяют, что поток и бакет на месте.

Обратный порядок тоже безопасен — узлы поднимутся при старом окне и будут
работать, слабее окажется лишь защита от повторов. Отдельного шага миграции
не нужно, `mesh bridge` делает это при старте.

Проверено на стенде с боевыми правами: агент при старом окне стартует и
поток не меняет, а изменить его не может даже намеренно — хаб отвечает
`Permissions Violation for Publish to "$JS.API.STREAM.UPDATE.MAIL"`.

**При первом запуске обновлённого моста человек может увидеть свои старые
сообщения повторно.** Позиция чтения обновлений теперь хранится в бакете
`bridge_state`, при первом старте он пуст, и Telegram отдаёт всё, что
накопил за сутки. Прежние письма имели случайные идентификаторы, поэтому
дедупликация их не отсеет. Дальше повторов не будет.

**Бакеты заводит приложение, а не человек.** `bridge_topics`, `bridge_state`
и `bridge_posted` создаются мостом через клиентскую библиотеку. Бакет,
созданный вручную через `nats` CLI, может оказаться без прямого чтения — и
тогда запись в него проходит, а чтение упирается в таймаут: отказ
наполовину рабочий и молчаливый.

## Резервное копирование

Состояние сети живёт в JetStream на VPS. Комментарий в коде когда-то
утверждал, что у моста нет состояния и бэкапить нечего, — это неверно:
состояние есть, просто оно не в файлах рядом с мостом.

Что теряется при потере хранилища:

| Поток или бакет | Что в нём | Чем грозит потеря |
|---|---|---|
| `MAIL` | все письма за 90 дней | переписка недоступна; новые письма ходят |
| `KV_mail_state` | позиция чтения каждого агента | агенты перечитают старые письма как новые |
| `KV_bridge_topics` | соответствие «тред — тема супергруппы» | продолжение разговора создаст вторую тему-дубль |
| `KV_bridge_state` | позиция чтения обновлений Telegram | человек увидит свои сообщения за сутки повторно |
| `KV_bridge_posted` | отметки о показанных письмах | витрина переиграет письма в канал заново |
| `KV_claims` | занятые зоны кода | снимаются мягкие захваты; агенты объявляют зоны заново |
| `KV_bridge_routes` | соответствие «пост в чате — разговор» | ответы на показанные посты перестают находить разговор; письма целы, человек получает внятный отказ |

`claims` поднимает мост вместе с остальной топологией — вызовом
`claims.EnsureBucket` рядом с `bus.EnsureBridgeTopology`. Отдельным вызовом, а
не внутри: пакет `bus` не может импортировать `claims`, вышло бы кольцо.

Прежняя версия этого документа обещала, что бакет создаётся лениво, при
первом захвате зоны, — а `hub.conf` рядом утверждал обратное. Не делал этого
никто: агент пробовал создать сам и упирался в отсутствие `STREAM.CREATE`,
причём молча. Отказ по правам в NATS асинхронный, поэтому клиент ждал ответа
до таймаута и сообщал `context deadline exceeded` — то есть выглядело это как
неполадка со связью, а не как «мост ещё не поднимал топологию».

### Процедура: остановить хаб и скопировать каталог

```bash
sudo systemctl stop nats-hub
sudo cp -a /var/lib/nats/jetstream /var/backups/mesh-$(date +%F)
sudo systemctl start nats-hub
```

Восстановление — тем же способом в обратную сторону:

```bash
sudo systemctl stop nats-hub
sudo rm -rf /var/lib/nats/jetstream
sudo cp -a /var/backups/mesh-2026-08-17 /var/lib/nats/jetstream
sudo chown -R nats:nats /var/lib/nats/jetstream
sudo systemctl start nats-hub
```

### Данных мало: без этих файлов их некуда возвращать

Копия хранилища спасает от порчи данных, но не от потери машины. Вместе с
ней в тот же архив (и **не в git**) кладутся:

| Файл | Что это | Восстановим? |
|---|---|---|
| `/etc/nats/hub.conf` | конфигурация хаба с публичными ключами всех узлов | да, но вручную — см. ниже |
| `/etc/mesh/bridge.nk` | **seed моста** | **НЕТ** |
| `/etc/mesh/bridge.env` | токен бота | да — перевыпускается у @BotFather |

`hub.conf` восстанавливается не тем способом, который приходит в голову
первым. **Запускать `mesh keygen` заново нельзя**: он выдаёт НОВЫЕ пары, и
все девять узлов разом теряют доступ — их старые seed-файлы перестают
подходить. Правильный путь: взять сохранённые seed-файлы узлов, получить из
каждого публичный ключ через `mesh keygen --show <файл>.nk` и собрать блок
`users` руками по образцу шаблона `nats/hub.conf`. То есть hub.conf
восстановим ровно настолько, насколько целы seed-файлы на самих машинах, —
а seed моста лежит только на VPS.

`bridge.nk` — единственное здесь по-настоящему невосстановимое. Из публичного
ключа приватный seed не выводится, а второй копии на VPS нет: туда он и
попадает единственным из девяти. Утерян — значит новая пара мосту и правка
блока прав в `hub.conf`, то есть перезапуск хаба и простой всей сети.
Держите защищённую копию отдельно от VPS.

Токен бота стоит того, чтобы не паниковать: перевыпуск у @BotFather занимает
минуту, старый при этом отзывается.

```bash
sudo tar -czf /var/backups/mesh-secrets-$(date +%F).tgz \
    /etc/nats/hub.conf /etc/mesh/bridge.nk /etc/mesh/bridge.env
sudo chmod 600 /var/backups/mesh-secrets-*.tgz
```

### Обязательный шаг: увезти копию с VPS

**`/var/backups` на самом VPS защищает только от порчи `store_dir`.** При
потере машины — диск умер, провайдер удалил, доступ утрачен — оба архива
погибают вместе с данными, ради которых их делали. Копия обязана лежать не
там.

```bash
# на своей машине, не на VPS
scp vps:/var/backups/mesh-$(date +%F).tar.gz      ~/backups/
scp vps:/var/backups/mesh-secrets-$(date +%F).tgz ~/backups/
chmod 600 ~/backups/mesh-secrets-*.tgz
```

Копию надо проверить, а не предположить. Проверка не печатает содержимое —
в архиве секреты, и им нечего делать ни в логе, ни в истории команд:

```bash
# читается ли архив: список файлов, без распаковки
tar -tzf ~/backups/mesh-secrets-$(date +%F).tgz
tar -tzf ~/backups/mesh-$(date +%F).tar.gz > /dev/null && echo "архив данных читается"

# совпадает ли с оригиналом: суммы считаются с обеих сторон
ssh vps "sha256sum /var/backups/mesh-secrets-$(date +%F).tgz"
sha256sum ~/backups/mesh-secrets-$(date +%F).tgz
```

Суммы разошлись — копия непригодна, и узнать об этом надо сейчас, а не в
день аварии.

**Проверено целиком на локальном стенде**: настоящий `nats-server` 2.14.5,
все пять хранилищ с различимыми данными, снимок, стирание каталога,
восстановление. После восстановления на месте оказались письма, позиции
чтения агентов, тема разговора, отметка о показе, TTL бакета отметок (48
часов) и окно дедупликации потока (сутки). Простой хаба на копировании 320
КБ — около трёх секунд, из них почти всё занимает перезапуск сервиса.

Цена способа — остановка хаба: во время копирования узлы отключены. Письма
при этом не теряются, агенты переподключаются сами, а мост забирает
накопленное durable-консьюмером. Для сети из девяти узлов это дешевле, чем
альтернатива ниже.

### Почему не `nats account backup`

Штатная команда `nats` CLI выглядит удобнее — она снимает копию по сети, без
остановки хаба, — но в нашей схеме неисполнима, и это проверено:

```bash
$ nats --server nats://127.0.0.1:4222 --nkey bridge.nk account backup --force /tmp/x
nats: error: context deadline exceeded
# в логе хаба: Permissions Violation for Publish to "$JS.API.STREAM.LIST"
```

Права `$JS.API.STREAM.LIST` нет ни у одной учётки в `nats/hub.conf` — ни у
агентов, ни у моста, — и выдавать его мосту не следует: оно раскрывает имена
всех потоков. Чтобы команда заработала, на хабе нужна отдельная
административная учётка; заводить её ради бэкапа, который делается раз в
сутки при остановленном сервисе, мы сочли неоправданным.

Отдельно: **без `--force` эта команда молча ничего не делает.** Запущенная
из скрипта или по `ssh` без терминала, она печатает
`cannot ask for confirmation without a terminal`, оставляет каталог пустым и
возвращает нулевой код возврата. То есть ночной бэкап по расписанию выглядел
бы успешным, а файлов бы не было.

### Чего эта проверка не покрывает

- Проверено на локальном стенде, **не на VPS**: там другой объём данных,
  другой диск и настоящий systemd-юнит.
- **Перенос копии с VPS и сверка сумм не проверялись вовсе** — VPS ещё нет.
  Шаги описаны, но ни `scp`, ни сверка `sha256sum` между машинами здесь не
  выполнялись.
- Не проверялось восстановление в хаб, где уже есть данные: процедура
  предполагает пустой каталог, и смешивать старое с новым мы не пробовали.
- Не проверялась работа сети во время остановки хаба. Основание, что узлы
  вернутся сами, есть в нашем же коде: `bus/conn.go` подключается с
  `MaxReconnects(-1)` и `ReconnectWait(2 * time.Second)` — попытки
  бесконечные, пауза две секунды. Но **живьём остановку хаба под нагрузкой
  мы не проверяли**: код говорит о намерении, а не о результате.

Мост, поднятый на пустом хранилище, создаст топологию заново — пустую. Это
означает, что «восстановление» без бэкапа выглядит как успешный старт: все
семь хранилищ на месте, TTL и окно дедупликации правильные, данных нет.
Проверять надо содержимое, а не наличие потоков.

Хранилищ именно семь: `MAIL`, `KV_mail_state`, `KV_bridge_topics`,
`KV_bridge_state`, `KV_bridge_posted`, `KV_claims` и `KV_bridge_routes`.
Число росло дважды: шестым стал реестр зон, когда его начал поднимать мост,
седьмым — маршруты ответов вместе с темами проектов.


## Что в этой процедуре не проверено

Честный список — ни один из пунктов не выдаётся за пройденный.

- **`make hub-check` разбирает шаблон**, подставляя одноразовые ключи и
  самоподписанный сертификат. Структуру и права он стережёт; правильность
  настоящих ключей и сертификата — нет.
- **Продление сертификата по расписанию.** Механизм проверен целиком, но
  принудительным прогоном: `certbot renew --force-renewal` выпустил новый
  сертификат, хук положил копию и перезагрузил хаб, сервер снаружи стал
  отдавать новый серийный номер, соединения при этом не рвались. Что таймер
  certbot сработает сам, не проверено — первое настоящее продление наступит
  за тридцать дней до конца срока.
- **Резервное копирование и восстановление** — см. раздел выше: на VPS
  команды не выполнялись. Отдельно: проверка восстановления проводилась,
  когда хранилищ было пять. Шестой и седьмой, `KV_claims` и
  `KV_bridge_routes`, ею не покрыты. Практически
  он безобиден — захваты мягкие и живут восемь часов, потеря реестра значит
  «объявите зоны заново», — но утверждать, что бэкап его переживает, мы не
  можем.
- **`darwin/arm64` из `make cross` не запускался**: на маке работает
  нативная сборка. `linux/arm64` проверен — именно этот артефакт работает на
  VPS и на Pi.
- **Отсев чужого чата** покрыт юнит-тестом, живьём не проверялся.
- **Два моста на одном токене** будут воровать друг у друга обновления:
  `getUpdates` отдаёт обновление одному потребителю. В коде этому ничего не
  мешает.
- **Поведение `Monitor` после `/compact`** проверено: процесс сторожа и
  доставка уведомлений сжатие переживают. Не проверено поведение после
  нескольких сжатий подряд и то, кто перевзводит сторожа в новой сессии.
- **Всё, что зависит от поведения самого Telegram.** Интеграционная приёмка
  шла против ДВОЙНИКА Bot API: настоящих токена и супергруппы на стенде не
  было. Не проверены реальные коды ошибок, поведение forum topics, режим
  приватности бота и настоящий лимит частоты. Ограничитель выдерживает
  заданные три секунды между сообщениями — соответствие реальному лимиту
  Telegram и обработка настоящего 429 не проверялись.
- **Мост как целое интеграционно не собирается.** Адрес Bot API зашит внутри
  `bridge.Run`, поэтому стенд поднимает его половинки по отдельности и
  повторяет часть кода у себя. Проверяется копия того, что работает в бою.

Если при развёртывании обнаружится расхождение с этим документом — это дефект
документа, а не повод обходить его молча.
