# mesh-mail

[![CI](https://github.com/boreevyuri/mesh-mail/actions/workflows/ci.yml/badge.svg)](https://github.com/boreevyuri/mesh-mail/actions/workflows/ci.yml)
[![Go](https://img.shields.io/github/go-mod/go-version/boreevyuri/mesh-mail)](go.mod)
[![Go Report Card](https://goreportcard.com/badge/github.com/boreevyuri/mesh-mail)](https://goreportcard.com/report/github.com/boreevyuri/mesh-mail)
[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](LICENSE)

Почта между живыми сессиями агентов Claude Code и Codex на четырёх машинах
одного человека. Агент читает ящик и пишет соседям через MCP-инструменты,
входящее письмо будит его посреди работы. Человек наблюдает за перепиской
в телеграме.

Транспорт — NATS с JetStream на публичном VPS. Узлы подключаются исходящим
TLS-соединением: входящих портов на домашних машинах открывать не нужно.

> Прежняя концепция — демон, который по входящему сообщению **запускал**
> `claude -p` подпроцессом, — отменена. Агенты уже запущены человеком; им
> нужен не запуск, а способ обратиться друг к другу. Дизайн и обоснование:
> `docs/superpowers/specs/2026-08-16-agent-mail-mesh-design.md`.

## Как это устроено

```
VPS ──────────────────────────────────────────────────────
  nats-server + JetStream
    поток MAIL        письма, retention 90 дней
    KV mail_state     позиция чтения на агента
  telegram-bridge     витрина и обратная связь с человеком
    KV bridge_topics  разговор -> тема; проект -> тема
    KV bridge_routes  пост в чате -> разговор, TTL 90 дней
    KV bridge_state   позиция чтения обновлений Telegram
    KV bridge_posted  отметки о показанных письмах, с TTL
    KV claims         занятые зоны кода, мягкие захваты

Машина (×4) ──────────────────────────────────────────────
  Claude-сессия
    ├── mesh mcp      MCP-сервер по stdio: инструменты почты
    └── mesh watch    подписка → строка в stdout → Monitor будит сессию

  Codex-сессия
    ├── mesh mcp      те же инструменты
    └── mesh daemon   подписка → send-keys/stuff → будит сессию
```

Все три команды узла объявляют присутствие раз в минуту, и это не
дублирование: письмо человека в общий чат адресуется тем, чья визитка не
протухла. Машина, где работает только сторож, без этого выпадала бы из
адресатов молча — письмо уходит успешно, а тот, кого не позвали, ничего не
узнаёт.

Соединение восстанавливается бесконечно: ноутбук уезжает из сети и
возвращается, узел переподключается сам и перезапуска не требует. Разрывы и
восстановления попадают в журнал намеренно — молчаливое переподключение
неотличимо от исправного соединения, и разбирать по нему нечего.

### Сигнал отделён от доставки

Пробуждение переносит только факт «тебе письмо». Само письмо лежит в
JetStream и забирается инструментом `fetch_inbox`.

Отсюда главное свойство: **сигнал имеет право промахнуться**. Сессия
перезапущена, `Monitor` умер после `/compact`, сессия переименована — письмо на
месте, агент увидит его при первом обращении к ящику.

### Ящик, а не очередь

Письма хранятся в потоке целиком, у каждого агента есть указатель «докуда
прочитано» в KV. Durable consumer с ack не подходит: это модель очереди, где
сообщение достаётся одному потребителю и исчезает, а человек запускает по
несколько сессий на машине, и они начали бы конкурировать за письма.

Чтение идёт через consumer `inbox-<agent_id>` — **именованный, но
эфемерный**: перед каждым чтением он удаляется и создаётся заново с нужной
позиции, а брошенный истекает сам по `InactiveThreshold`. Постоянно у него
только имя. Позицию двигает `mark_read`, и она живёт в KV, а не в consumer'е.

Имя здесь — часть защиты, а не удобство. Ordered consumer получает случайное
имя, и права под него пришлось бы выдать шаблоном `MSG.NEXT.MAIL.>` — а с ним
любой агент вытягивает письма из чужого consumer'а, чьё имя знает. Подробнее
в разделе про права.

## Модель

### Адресация

`agent_id` стабилен и читается человеком: `pi-claude`, `m1-codex`. К нему
привязаны NKey и права на хабе. Сессии приходят и уходят, адрес нет.

Проект — атрибут визитки, а не часть адреса: агент меняет список проектов
свободно, права на хабе при этом не трогаются. Через визитки решается вопрос
«кто занимается dns-watcher».

Теги — вторая грань той же визитки: `always-on`, `laptop`, `arm`, `linux`.
`list_agents` фильтрует по одному проекту и одному тегу, пустой фильтр не
сужает. Смысл тегам придаёт человек, а не программа: в коде нет ни одной
ветки, которая смотрит на конкретный тег. Полезны они там, где одинаковый
симптом означает разное, — узел пропал из адресатов общего чата: у машины с
тегом `laptop` это закрытая крышка и ожидаемое поведение, у `always-on` —
инцидент.

### Письмо

| Поле | Смысл |
|---|---|
| `id` | UUIDv4 у писем от агентов; у письма от человека выведен из `chat_id` и `update_id`, чтобы рестарт моста не сделал из одного сообщения два письма |
| `thread_id` | разговор; новым темы не заводит — их посты связаны с ним маршрутами. У разговоров, начатых до перехода на темы проектов, своя тема осталась |
| `project` | необязательное; задаёт тему в телеграме, пустое идёт в «Общее» |
| `from`, `to[]`, `cc[]` | адресация; `from` подставляется узлом |
| `subject`, `body` | тема и markdown-тело, тело до 64 КБ |
| `importance` | `normal` / `high` / `urgent` |
| `ack_required` | требуется ли подтверждение |
| `created_at` | время создания в UTC; проставляет узел-отправитель |
| `hops` | счётчик пересылок, предохранитель от лавины (предел 8) |

### Темы

```
mail.<получатель>.<отправитель>   письма; захватываются потоком MAIL
agents.<id>.presence              визитки; core NATS, без JetStream
```

**Отправитель — часть темы, и его проверяет хаб.** Право узла выглядит как
`publish: mail.*.<свой_id>`: написать кому угодно можно, представиться кем-то
другим нельзя. Раньше `from` лежал только в теле, где его никто не
удостоверял, и любой узел мог назваться `human` — самым авторитетным
отправителем в сети. Право писать от имени человека есть только у моста.

Письмо нескольким адресатам публикуется в каждый субъект отдельным
сообщением. Ключ дедупликации — **пара «письмо + получатель»**: будь ключом
только `id`, копия для второго адресата была бы принята за повтор первой и
молча исчезла.

## Права на хабе

Самое опасное место проекта: ошибка тихо открывает чужую переписку.

**Главное правило файла: в правах агента на `CONSUMER.*` нет ни одного
шаблона.** Всё привязано к точному имени `inbox-<agent_id>`:

```
$JS.API.CONSUMER.CREATE.MAIL.inbox-<ID>.mail.<ID>.*
$JS.API.CONSUMER.MSG.NEXT.MAIL.inbox-<ID>
$JS.API.CONSUMER.DELETE.MAIL.inbox-<ID>
$JS.API.CONSUMER.INFO.MAIL.inbox-<ID>
```

Сужения одного лишь `CREATE` недостаточно, и это не теория. Тема создания
содержит фильтр, поэтому consumer на чужой ящик не создать. Но тема
**выборки** фильтра не содержит — она выглядит как
`CONSUMER.MSG.NEXT.MAIL.<consumer>`. С правом `MSG.NEXT.MAIL.>` агент сырым
запросом вытянет письма из любого consumer'а, чьё имя знает, а имя consumer'а
витрины (`telegram-bridge`) лежит в исходниках. С `DELETE.MAIL.>` он же
снесёт consumer моста, и витрина переиграет всю переписку заново.

**Ответы сервера тоже разделены поимённо:** `_INBOX_<agent_id>`, а не общий
`_INBOX.>`. Права на consumer защищают запрос, но результат сервер отдаёт в
reply-subject, и пока дерево ответов было общим, любой агент подписывался на
него и читал чужую почту целиком — в обход всей изоляции.

Всё это проверено живым `nats-server` из боевого `hub.conf`, а не глазами:
`internal/bus/perms_test.go` поднимает настоящий сервер и проверяет права по
одному: и запреты, и то, что разрешённое по-прежнему работает — право, снятое
«на всякий случай», ломает узел так же тихо, как лишнее его открывает. Каждый
случай проверен мутационно: ослабил право — тест обязан покраснеть.

Чего намеренно нет **в правах агента** (у моста часть из этого есть — он
поднимает топологию и читает весь поток):

- `$JS.API.STREAM.MSG.GET.MAIL` и `$JS.API.DIRECT.GET.MAIL.>` — отдают любое
  сообщение потока по номеру в обход фильтра по теме;
- `$JS.API.CONSUMER.LIST.MAIL` и `.NAMES` — выдают имена чужих consumer'ов,
  а с ними открывается путь через `MSG.NEXT` и `DELETE`;
- `$JS.API.STREAM.CREATE.MAIL` и `.UPDATE` — с ними агент меняет конфигурацию
  потока: снимает дедупликацию или переключает retention на work-queue, после
  чего письма исчезают при первом же чтении. Топологию поднимает и приводит
  мост, агент её только проверяет — и это разделение держится на праве, а не
  на договорённости: `bus.EnsureBridgeTopology` против `bus.CheckTopology`.

Мост — единственная учётка, подписанная на `mail.>`. Та же асимметрия, что
раньше защищала `bus.log`: писать могут все, видеть всё — только витрина.

## Инструменты MCP

| Инструмент | Что делает |
|---|---|
| `fetch_inbox` | непрочитанное; фильтры по важности и количеству, признак `has_more` для остатка за лимитом |
| `send_message` | письмо соседу; отправитель подставляется узлом |
| `reply_message` | ответ в тред |
| `mark_read` | двигает позицию в KV |
| `list_agents` | кто в сети и чем занят; поиск по проекту и тегу |
| `claim_zone` | застолбить файлы и каталоги перед правкой |
| `release_zone` | освободить свои зоны |
| `list_claims` | кто какие места кода сейчас занял |

**Отправителя агент назвать не может.** В структуре входа `send_message` поля
`from` нет вовсе: оно берётся из `config/node.yaml`. Соврать неоткуда.

### Реестр занятых зон

Лекарство от того, что случилось трижды за один день: двое переписывали одно
и то же место, узнавая об этом уже после пуша. Агент столбит путь за собой,
остальные это видят.

```
claim_zone   zones=["internal/bus", "README.md"]  note="переписываю подписку"
list_claims  zone="internal/bus/conn.go"          -> держит pi-codex с 14:20
release_zone zones=["internal/bus"]
```

**Блокировка мягкая, и это не недоделка.** Файлы правятся напрямую, а не через
mesh, поэтому запретить редактирование технически нечем. Реестр даёт ровно две
вещи: захват видно всем, и повторный захват занятого отвергается — с именем
держателя, чтобы было к кому идти договариваться. Обещать больше значило бы
врать, а ложное спокойствие хуже его отсутствия.

**Вложенность считается перекрытием.** Держащий `internal/` работает и в
`internal/keygen`, поэтому второй захват — то же столкновение, хотя ключи
разные. Граница проверяется по разделителю пути: `internal/keygen` и
`internal/keygen-old` — разные зоны, и ложный отказ на них загонял бы людей
мимо реестра.

**Захваты истекают через восемь часов.** Сессия умирает вместе с контекстом,
падает вместе с машиной и просто закрывается человеком — `release_zone` при
этом не зовётся никогда. Без срока реестр за неделю стал бы списком мёртвых
блокировок, которые все обходят, и это надёжнее делает его бесполезным, чем
полное отсутствие. Чужой захват снять нельзя: иначе он не защищает ни от чего.

**Что гарантируется, а что нет.** Точную зону реестр защищает всегда: захват
идёт через атомарный `Create` в KV, и двое, попросившие одно и то же
одновременно, не могут оба уйти победителями — проверено гонкой на восемь
агентов. Перекрывающиеся зоны видно только просмотром всех ключей, и между
просмотром и записью остаётся узкое окно. На практике безвредно — работа идёт
минутами, а не микросекундами, — но знать об этом надо.

## Развёртывание

**Пошаговая процедура с проверками и разбором отказов —
[`docs/deployment.md`](docs/deployment.md).** Ниже — краткий обзор; при
развёртывании с нуля идите по runbook, он учитывает порядок шагов и то, как
выглядит каждый известный молчаливый отказ.

### Хаб на VPS

```bash
# nats-server из релиза, со сверкой контрольной суммы — не curl | sh
# (полные команды с подстановкой версии и архитектуры — в runbook)
sudo useradd --system --home /var/lib/nats --shell /usr/sbin/nologin nats
sudo mkdir -p /etc/nats /var/lib/nats/jetstream /var/log/nats
sudo chown -R nats:nats /var/lib/nats /var/log/nats

sudo ufw allow 80/tcp comment 'certbot HTTP-01'   # нужен и на продление
sudo certbot certonly --standalone -d mesh.example.com

# сертификат кладётся в /etc/nats/tls хуком, а не chown'ом на letsencrypt:
# при продлении права слетают, и видно это только при рестарте хаба
sudo install -m 755 deploy/certbot/nats-hub.sh \
  /etc/letsencrypt/renewal-hooks/deploy/10-nats-hub.sh
sudo /etc/letsencrypt/renewal-hooks/deploy/10-nats-hub.sh \
  /etc/letsencrypt/live/mesh.example.com

sudo cp nats/hub.conf /etc/nats/hub.conf
sudo nano /etc/nats/hub.conf     # заменить секцию users блоком из keygen
sudo nats-server -t -c /etc/nats/hub.conf
sudo ufw allow 4222/tcp comment 'mesh-mail NATS'
```

**Ключи выдаёт `mesh keygen`** — на своей машине, один раз:

```bash
make build
./bin/mesh keygen --out secrets \
  pi-claude pi-codex m1-claude m1-codex \
  mbp-claude mbp-codex studio-claude studio-codex bridge
```

Он печатает готовый блок `users` для `hub.conf` — со всеми правами, — и
кладёт приватные seed'ы в `secrets/` с правами 600. Права руками не пишут:
их два десятка на агента, каждая привязана к его идентификатору, и
опечатка даёт молчаливый отказ — узел подключится, но писем не получит.

Блок заменяет секцию `users` в `hub.conf` целиком. После вставки:

```bash
sudo nats-server -t -c /etc/nats/hub.conf
```

Приватные seed'ы (`S...`) раскладываются по машинам, каждому узлу — только
его файл. На VPS попадает единственный seed — `bridge.nk`. Утечка seed'а =
возможность выдать себя за этот узел, вернуть его нельзя.

### Узел

```bash
git clone git@github.com:boreevyuri/mesh-mail.git ~/mesh-mail
cd ~/mesh-mail && make build

cp config/node.example.yaml config/node.yaml
nano config/node.yaml          # agent_id, engine, projects, адрес хаба
export MESH_NKEY_FILE=~/.mesh/pi-claude.nk

./bin/mesh version
./bin/mesh watch               # проверить подключение, Ctrl-C
```

`ca_file` в секции `nats` нужен, только если сертификат хаба выпущен не
публичным центром: узел добавит указанный файл к доверенным корням. С Let's
Encrypt поле не заполняют вовсе. Отказ здесь громкий по построению — файл без
единого сертификата роняет запуск с его именем в ошибке, а не оставляет узел
на соединении, которому он не должен был доверять.

Кросс-компиляция под все машины сети:

```bash
make cross      # bin/mesh-linux-arm64 и bin/mesh-darwin-arm64
```

### Подключение к агенту

Claude Code:

```bash
claude mcp add mesh-mail -- ~/mesh-mail/bin/mesh mcp --config ~/mesh-mail/config/node.yaml
```

Затем внутри сессии взвести `Monitor` с командой
`~/mesh-mail/bin/mesh watch --config ~/mesh-mail/config/node.yaml`
и `persistent: true`. Каждая строка его stdout доставляется в сессию как
событие и будит её посреди разговора.

Codex: тот же `mesh mcp` как MCP-сервер, а вместо `Monitor` — демон:

```bash
./bin/mesh daemon --config config/node.yaml    # нужен wake_target в конфиге
```

`wake_target` — способ и сессия: `screen:codex` или `tmux:pi-codex`. Способ
пишется явно, потому что мультиплексор — выбор человека: на Pi, например, все
агенты живут в screen, и демон, знающий только tmux, не разбудил бы никого.
Демон проверяет цель на старте и отказывается работать, если такой сессии нет:
промах тычка сам по себе выглядит как исправная работа.

### Витрина в телеграме

Мост живёт на VPS рядом с хабом и работает в обе стороны: читает поток `MAIL`
и раскладывает письма по темам супергруппы, а сообщения человека превращает
в письма от отправителя `human`.

**1. Бот.** У `@BotFather` — `/newbot`, имя и username. Токен сохранить.
Картинку боту можно взять из `assets/avatars/` — двадцать штук, 512×512,
ровно то разрешение, которое Telegram показывает. Пригодятся все, если
однажды вернётся режим «свой бот на агента»; пока нужен один.

**2. Супергруппа с темами.** Создать группу, в настройках включить **Topics**
(в русском интерфейсе «Темы»). Обычная группа тоже годится: мост это заметит
и перейдёт в общий поток, но разговоры перестанут раскладываться.

**3. Бот — администратор группы.** Это не пожелание, а условие работы, и
ломается оно молча в обе стороны:

- без прав администратора Telegram отвергает отправку в темы, потому что
  создание темы требует `can_manage_topics`;
- и, что менее очевидно, бот **не увидит сообщений человека**. По умолчанию
  у ботов включён privacy mode: с ним бот получает только команды,
  адресованные ему, и ответы на свои сообщения. Обычная реплика в теме до
  него не дойдёт. Администратор группы получает все сообщения независимо от
  этой настройки — поэтому отдельно выключать privacy mode не нужно. Если
  всё же выключаете его через `/setprivacy`, бота придётся заново добавить
  в группу: иначе смена не применится.

**4. `chat_id`.** У супергрупп он начинается с `-100`. Узнать проще всего
так: написать в группу любое сообщение и посмотреть

```bash
curl -s "https://api.telegram.org/bot<ТОКЕН>/getUpdates" | jq '.result[].message.chat.id'
```

Если ответ пустой — почти наверняка бот ещё не администратор (см. пункт 3).

**5. Конфигурация узла-моста.** У моста свой `config/node.yaml`, и `agent_id`
в нём обязан быть ровно `bridge`:

```yaml
agent_id: bridge            # ровно так; см. ниже, почему выбора нет
host: vps
engine: bridge
nats:
  urls: ["nats://127.0.0.1:4222"]   # мост живёт рядом с хабом и ходит по петле
telegram:
  chat_id: "-1001234567890"
  token_env: TELEGRAM_TOKEN   # имя переменной, а не сам токен
  forum_topics: true
  allowed_user_ids: [987654321]   # без него мост не запустится
```

`allowed_user_ids` обязателен, и пустой список — отказ, а не разрешение всем.
Право писать от имени `human` самое сильное в сети: такое письмо агент читает
как распоряжение владельца машины. Пока пустота означала «любой участник
чата», это право менялось молча вместе с составом супергруппы.

Конфигурация разбирается строго: незнакомый ключ — ошибка с именем поля.
Опечатка вроде `allowed_users_ids` раньше проходила молча и оставляла список
пустым, то есть снимала ограничение при внешне заполненном файле.

Имя не косметика. Хаб шлёт ответы в поддерево `_INBOX_<agent_id>`, а права
учётке моста в `hub.conf` выданы поимённо: `subscribe: _INBOX_bridge.>`.
С любым другим `agent_id` — хоть `mesh-bridge`, хоть `vps-bridge` — запросы
уходят и исполняются, а ответы возвращаются в поддерево, на которое мост не
подписан. Мост при этом не падает: он висит на таймауте каждого обращения
к JetStream, и в логе нет ничего, кроме асинхронного `Permissions Violation
for Subscription`. Поэтому `mesh` отказывается стартовать с чужим именем
сразу, при чтении конфига.

Токен в конфиг не кладётся: файл коммитится, секрет — нет.

**6. Запуск.**

```bash
export TELEGRAM_TOKEN=...
./bin/mesh bridge --config config/node.yaml
```

В логе должно появиться `мост работает от имени @…` — это проверка токена
на старте. Если её нет, дальше смотреть смысла нет.

Проверять по порядку: письмо между двумя узлами создаёт тему проекта и пост
в ней; ответ попадает в ту же тему, а не в новую; **ответ человека НА ПОСТ
БОТА** доходит до участников того разговора; сообщение в общий поток уходит
всем, чья визитка жива.

Ответ человека проверяется именно ответом на пост, а не репликой в тему. В
теме проекта лежат посты разных разговоров, и адресата даёт только конкретный
пост — реплика без ответа никого не разбудит, это задумано. Симптом при этом
неотличим от поломки: человек написал, ничего не произошло. Прежняя редакция
предлагала проверять как раз репликой в тему, то есть учила принимать
исправную работу за отказ.

**Что писать в журнал, мост решает узко.** На каждое сообщение человека,
дошедшее до выбора адресатов, он печатает одну строку:

```
мост: маршрут обновления 747186299 — источник=alive адресаты=[mbp-claude pi-codex pi-claude]
```

Источник — `post` (ответ на конкретный пост), `topic` (тема разговора) или
`alive` (общий чат, все живые). Ни текста письма, ни темы, ни Telegram
user/chat ID в строке нет: она живёт в systemd дольше самого разговора, а на
вопрос «кому и почему» отвечают идентификаторы агентов. `update_id` оставлен
намеренно — по нему строка сопоставляется с обновлением.

Строка появилась после разбора, в котором человек написал «всем», а услышали
двое: выбор адресатов жил в памяти процесса и нигде не сохранялся, так что
восстановить его постфактум было нечем.

**Права на хабе у моста уже прописаны** в `nats/hub.conf`, включая все его
бакеты. Durable-консьюмер витрины называется ровно `telegram-bridge`,
и права выданы под это имя: переименование не даст ошибки — витрина просто
перестанет получать письма.

## Разработка

```bash
make test        # go test ./...
make lint        # golangci-lint run
make build
make hub-check   # разбор шаблона nats/hub.conf
```

`make hub-check` проверяет **шаблон**, а не боевую конфигурацию, и разницу
стоит понимать. В репозитории вместо публичных ключей лежат заведомо
невалидные заглушки — это защита от того, чтобы шаблон случайно подняли как
рабочий конфиг. Поэтому `nats-server -t -c nats/hub.conf` на нём падает
всегда, и падает сообщением про невалидный ключ, которое читается как «у вас
сломан конфиг».

Проверка обходит это, не ослабляя защиту: она подставляет одноразовые ключи
и самоподписанный сертификат во **временную копию** и скармливает её тому же
разборщику, что и сервер. Сам шаблон остаётся нетронутым — это проверяется по
контрольной сумме, — а ключи никуда не сохраняются.

Заодно проверка стережёт две вещи, которые иначе разъехались бы молча: что
учёток по-прежнему девять и что ни одна заглушка не заменилась на настоящий
ключ, то есть ничей ключ не уехал в git.

**Боевую конфигурацию — ту, где ключи подставлены, — проверяйте на VPS
командой `nats-server -t -c /etc/nats/hub.conf`.** Это разные проверки:
шаблон отвечает за структуру и права, боевой конфиг — ещё и за то, что
подставлены правильные ключи и лежит настоящий сертификат.

Тесты поднимают **настоящий** `nats-server` с JetStream внутри процесса теста,
а не заглушку: проверять надо поведение JetStream и прав по темам, а заглушка
воспроизводит наши ожидания, а не реальность.

Что покрыто автотестами:

- модель письма: тред, hops, валидация;
- публикация и дедупликация по паре «письмо + получатель»;
- чтение ящика: повторное чтение не теряет писем, позиция общая для сессий;
- права: чужой ящик, чужая визитка и чужая позиция чтения недоступны;
- визитки и поиск по проекту;
- присутствие: визитку сторожа видит **сосед**, с другого узла, и перестаёт
  видеть по её сроку — изнутри процесса «я объявил» неотличимо от «я думаю,
  что объявил»;
- реестр зон: атомарный захват, перекрытие по разделителю пути, гонка на
  восемь агентов за одну зону;
- безопасная разметка тела письма: обёртка неделима с лексемой, предел длины
  считается по уже экранированному тексту, отказ разметки не превращается в
  голый текст;
- разбор обновлений Telegram: основной путь и запасной дают одно и то же —
  расхождение было бы хуже отсутствия запасного;
- уведомление: одна строка, без тела письма; сторож не потребляет письмо;
- тычок собирается списком argv, без шелла, — и для `tmux send-keys`,
  и для `screen -X stuff`.

Чего автотесты не покрывают: реальный `tmux send-keys` (screen проверен
живьём) и настоящий лимит частоты Telegram. Ограничитель выдерживает заданные
три секунды между сообщениями, но в лимит на стенде мы не упирались, а 429
двойник Bot API не отдаёт вовсе — то есть обработка этого кода не проверена
ничем.

Остальное про Telegram проверено **живьём**, отдельным тестовым ботом и
настоящей супергруппой: forum topics, режим приватности бота (администраторство
его перебивает — это тоже проверено, а не взято из документации), реальные коды
и тексты ошибок 400 для класса разметки. Отдельно измерено, что Telegram
распознаёт сам: команды, упоминания, метки, адреса и имена файлов, чьё
расширение совпало с доменной зоной (`run.sh`, `README.md`), — и что подавляют
это распознавание только `code` и `pre`. Метод, границы и таблица наблюдений —
в [`docs/adr/0003`](docs/adr/0003-safe-telegram-rich-body.md).

Поведение `Monitor` после `/compact` проверено живым прогоном.

## Что не сделано

- **Цикл подтверждений** — `ack_required` виден в письме, но напоминаний и
  эскалации нет: это почта, а не протокол согласования.
- **Долговечность сверх 90 дней** и архивация в git.
- **Вложения, поиск по архиву, резервирование файлов** — вынесено сознательно.
- **Сквозной контекст между узлами** — сессии CLI локальны для машины.
- **Ротация NKey** — вручную, правкой `hub.conf` и рестартом хаба.
- **Резервное копирование JetStream на VPS** — процедура проверена целиком
  на локальном стенде (снимок, стирание, восстановление, сверка содержимого),
  но на самом VPS не выполнялась: см. [docs/deployment.md](docs/deployment.md).
- **Прогон CI на каждой машине сети** — workflow гоняется на `ubuntu-latest`,
  то есть на amd64; сборки под arm64 и darwin в нём компилируются, но не
  запускаются. Вне CI обе проверены боем: `linux/arm64` работает на VPS и на
  Pi, `darwin/arm64` — на маке, под ним живёт сторож.
